ERP owns commercial orders/customer masters, content/prices/due allocation, branch/user/role administration, preparation/initial assignment, native actual receipt/disposition, stock and financial settlement. Tawsel owns accepted delivery snapshots, task/cycle/assignment execution, workdays/trips, plans/forecasts, attempts/outcomes/reported collection, progress and durable delivery intent. Credentials belong to the shared trusted issuer, with independent ERP/Tawsel sessions. The connector translates supported ERP mechanisms into this public HTTP/event language; it may be built by the ERP vendor/agency, Tawsel or both.

Begin feasibility discovery with the ERP’s supported APIs, webhooks, authentication, stable IDs, integration modules, import/export and vendor-supported extension mechanisms. Missing mechanisms may require vendor cooperation or an ERP-side adapter. No ERP source/database access or common internal schema is required. Consumers use public URLs and credentials when released; they never import Tawsel domain/repository code, query its database or call its private Nominatim/OSRM/VROOM adapters.

## Bootstrap and source obligations — P08 implemented / P10 designed

1. Provision authorized tenant/integration binding out of band through the P08 bootstrap flow; its command is `integration.bindSource`. No self-selected body tenant can grant scope. Configure source command credentials separately from webhook signing secrets. Rotate/disable with recorded state and explicitly scoped access. The exact P08 credential contract is in [provisioning](provisioning.md); production issuer deployment remains P39 work.
2. Project versioned source branches, users, trusted subject links, one role, user exceptions, memberships and driver/profile references. Apply source revisions monotonically; duplicate same revision/content is stable, conflicting content is rejected, and older updates cannot resurrect disabled access. Issuer changes run from durable reconciliation intent outside application transactions.
3. Authenticate service **and** verify bound user context for human-owned operations, or use an explicitly delegated service operation. `assertedActorId` in the generic envelope never suffices. Audit both service and actor. P08 implements expiring source-scoped credentials, explicitly allowed service actions and rotation with forged-context tests; it rejects human assertions rather than accepting unverified delegation. No real username, password, secret or bearer token belongs in a delivery payload.
4. Map stable task/order/source-dispatch/line references to Tawsel UUIDs. Scope by tenant/integration plus entity namespace; line IDs also belong to a task. Do not derive identity from phone/address, and never reuse a retired source ID for unrelated goods. Persist the mapping in the connector’s own storage.
5. Submit generic customer/contact, source address and location provenance, delivery instructions and optional earliest/window/service duration/priority snapshots. Source task reference, revision, contact and usable destination information are required foundation concepts. `DeliverySnapshot` is a reusable common shape, **not the completed B2B intake request**: P10 adds branch/driver, lines, splitting permission, exact due amounts/allocation and dispatch rules. P09's implemented personal path remains simple B2C without item/custody fields and rejects company/service principals.
6. Prepare separately from definitive received assignment. The latter asserts physical receipt and undergoes atomic admission, including active-plan capacity. A rejected batch accepts no subset and creates no phantom holder. Record source intent/pending until Tawsel acceptance is known. The accepted receipt survives Engine outage; planning status stays separate.

Authorized predeparture withdrawal/reassignment needs no mandatory reason or extra handover. Online start wins/loses that race under shared invariant locks. After departure, staff cannot alter execution contents/details/urgency. Only assigned-driver execution and the narrow actual source-branch receipt/disposition operations apply. Redispatch requires actual receipt and a new cycle, never reopening the returned cycle. See [state ownership](tracking-and-consistency.md).

## Common wire rules and command acceptance

- UUIDs are lowercase UUID strings. Opaque external IDs have maximum length 256 and are meaningful only in their source scope. Empty string is not missing/null. IDs are not authorization.
- Quantities are whole nonnegative pieces bounded by JavaScript’s exact integer range; fields requiring goods use a positive count. Money is `{amountMinor, currency, exponent}`, nonnegative exact integers, matching source currency/exponent. EGP exponent is 2. Other currency support must be validated by deployment/source policy, not inferred from a three-letter string. Totals must also stay in the exact integer range; no float calculations, cross-currency sums or invented deposit allocation.
- Missing optional fields mean not supplied; null is accepted only where explicitly declared (`observedAt`, `nextCursor`). An optional value does not imply zero, false or permission. This full-snapshot foundation does not define PATCH/clear semantics. Feature owners specify replacement/clearing rules. Omitted service duration uses the accepted 600-second customer default in feature logic, not validator mutation; branch service remains separately configured. Omitted priority means ordinary when the feature defines its default. Time windows are generic constraints, not promised appointments; P10/P13 check chronological and eligibility consistency.
- Times are UTC RFC 3339 with `Z`; display `Africa/Cairo`. `observedAt`/clock quality, `receivedAt`, and business `committedAt` remain distinct. For events, `committedAt` is the transaction committing the event’s represented fact: an `evidence.received` event proves evidence receipt only, not acceptance of the underlying driver command.
- `schemaVersion` identifies the envelope reader, `payloadVersion` the operation/event payload reader; both current foundation readers accept `1.0.0` only. Each feature must register its exact operation/event payload before handling it. Arbitrary `payload` objects passing envelope validation are **not authorized/validated business commands**.
- `baseVersions` contains relevant distinct source/resource/outcome, route, assignment and device values. Feature schemas make applicable fields mandatory. A route-only revision change does not blanket-reject a compatible task/attempt result. Validate assignment/attempt/content/owner and dependencies against authoritative state.
- Scope idempotency by tenant, stable authenticated command source and action ID. Same semantic input returns its durable existing result; changed input gives `409 idempotency_conflict`. P05 fixes hash canonicalization and concurrent commit behavior. Query `action.getResult` or resend the same action after unknown response; never retry with a fresh ID by default. Missing dependency gives `dependency_missing`; it does not permit out-of-order acceptance.
- Every accepted command commits state/progress/history/audit/idempotency/outbound intent together. No issuer, Engine or ERP HTTP inside the transaction. `EvidenceReceipt` can be pending/rejected/review-required after durable receipt without a business commit. Applied ERP status is a different protocol observation.
- Reads use bounded cursor pagination (foundation default proposal 50, maximum 100), scoped stable snapshot revision and next cursor. Feature owners specify cursor expiry/filter binding. Coherent monitoring uses ETag/conditional refresh and rejects regressing revisions; P24 completes exact response/header schemas. Neither pagination cursor nor recipient sequence is a route revision.

Errors use the canonical `Problem` object (`type`, `title`, HTTP `status`, stable `code`, correlation ID, retryability; optional action ID/detail). JSON is not enriched with secrets/contact dumps. `application/problem+json` is the designed media type. Error examples cover validation, over-limit admission, invalid pin, unauthorized/forbidden resource, forbidden departed edits, stale revision/device, unsupported price allocation, missing/unavailable dependency, unassigned routes, unknown result and expired replay. HTTP 401 means authenticate again; 403 does not authorize changing account IDs. 409 requires reconciling the named conflict; 422 requires correcting supported input; 503 requires recovery/retry with the same action identity. Envelope/schema validity alone cannot prove these runtime statuses.

## Signed delivery and recovery — P25/P26

Tawsel writes outbound intent with the business transaction, including recipient-scoped event identity, aggregate, sequence and correlations. P25 claims with short leases, sends outside the database transaction, records attempt/result, and recovers expired leases. Retries preserve event ID and body; each transmission uses a fresh signing timestamp. A failing integration must not starve others. Proposed jittered exponential retry is capped at five minutes; failures remain visible until resolved.

The designed signing obligation is authentication of the **exact transmitted body bytes** with a tenant/integration-scoped rotated secret, algorithm/key identifier and delivery timestamp. P25 finalizes algorithm, header names, canonical signature input, replay skew/window, constant-time verification, key overlap/retirement, size limits and test vectors before any wire release. Do not implement against invented header examples now. Authenticate recipient binding, timestamp and schema before accepting; event ID deduplication remains necessary despite a fresh retry signature. Webhook URL administration needs destination/network controls and isolated test exceptions; it is not an arbitrary outbound request proxy.

Receiver stores verified event in its own durable inbox before acknowledging **received**. It applies projection and processed marker in one ERP-local transaction, then separately exposes/reports applied checkpoint or failure (`integration.reportAppliedCheckpoint`). Lost acknowledgement causes safe redelivery. HTTP 2xx or `deliveryStatus=received` never implies applied, business acceptance of another command, branch stock, inventory valuation or settlement. A reference receiver must use its own credentials/storage and public artifacts only.

Sequence scope is `(tenant, recipient integration, aggregate type, aggregate ID)` after visibility filtering, starting at 1. No global contiguous sequence revealing hidden events. Consumers track each scope, deduplicate by event ID, detect gaps, and buffer/request replay without applying unsafe transitions out of order. Feature payload revisions differ from this sequence. `progress.snapshot` is a replacement view with a snapshot revision: an older view may be ignored, but mandatory outcome/quantity/receipt/correction transitions retain distinct event IDs and cannot be discarded because a later view exists.

Replayable event payloads and complete command retry responses have a **proposed minimum 30-day retention**, with identity/result tombstones for the business record’s life and unresolved/failed/unprocessed work retained until resolved. No automatic business-history purge is enabled in this pilot foundation. P25/P26 must publish actual configured retention and expiry semantics. `410 replay_expired` directs the consumer to scoped reconciliation snapshot/checkpoint recovery; never synthesize historical financial transitions from current totals. Retain audit gaps explicitly. Event recovery does not recover unsent phone evidence lost with the device.

## Compatibility and old queued actions

Foundation is unreleased. Once released, canonical schemas for a published version are immutable. HTTP path major version, envelope version and feature payload version are separate compatibility axes; stable operation IDs remain recognizable across supported versions. P08 advertises supported versions at source binding; actual URL layout is completed by each owner. P08 GET /api/v1/provisioning/configuration exposes supported versions and service operations.

Current envelopes are closed outside their explicit payload object. Adding a field to a closed schema is **not** automatically backward compatible. Publish a new schema version or optional versioned payload reader; negotiate recipient capabilities before producing a version it cannot read. Within a feature payload deliberately designed for additive extension, optional fields may be additive only after old-reader and old-client tests prove it. Do not silently add a required field, change units/null meaning/enum semantics or reinterpret existing IDs. Unsupported versions produce explicit durable rejection/review status; they never authorize stripping data and guessing intent.

P34/P35 retain readers/upcasters for old offline payloads and local storage versions during deployments. Preserve the original bytes/semantic content, schema version, action ID, account/device identity and dependency chain; record any deterministic transformation and provenance. Example: adding an optional delivery note cannot discard a queued v1 two-piece action. The v1 reader remains available; a missing optional note stays absent. Adding required allocation information cannot reinterpret missing information as zero: keep the action as received review/rejected evidence with a recoverable explanation until a supported resolution exists. Never mint a new action ID merely to upgrade it.

Roughly 24 hours offline is a support target, not the cutoff for accepting/storing old evidence. Do not retire a reader while unresolved supported queues may depend on it without a tested retention/migration/recovery plan. Long-offline, expired-session and former-device evidence survives; current authorization and correction dependencies still decide whether it can affect business state. Same-account reauthentication, durable action-status recovery and safe update ordering are mandatory. Neither incompatible payloads nor unknown event types are silently acknowledged as business-applied.
