## Fixed reasons and ordinary driver authority

One `rejection` object applies to a whole B2B refusal or the rejected portion of B2B partial delivery. It is not per line. It has `catalogVersion:"1.0.0"`, one code below, and `detail` only for Other. The product catalog is fixed; there is no company catalog management capability.

| Code | Meaning |
| --- | --- |
| `changed-mind` | Changed mind / no longer needed |
| `amount-disagreement` | Amount different from agreement |
| `wrong-product` | Product different from order |
| `condition-problem` | Product/package condition problem |
| `inspection-unavailable` | Agreed inspection unavailable |
| `missing-pieces` | Missing pieces |
| `other` | Other, with written detail |

Other requires 1–500 Unicode characters, non-whitespace text and at least one printable letter, number, punctuation or symbol; whitespace/control/format-only text is rejected. Unknown catalog/code and irrelevant detail are rejected by closed schemas. Full delivery and no-answer reject rejection metadata. B2C keeps its simple refusal/no-answer/collection rules and forbids product reasons. Missing pieces describes refusal: it never changes delivered quantity, confirms loss/damage, creates a stock movement or authorizes compensation.

The driver remains an authenticated human with own execution and current device/round authority. Source credentials cannot impersonate the driver. Reasons flow through immutable IndexedDB actions, human validation, accepted records, original/effective history, correction replacements, signed events, replay and reconciliation. Corrections preserve original reasons and append replacement history; existing correction dependency/custody locks remain enforced.

No-answer is available at heading and after an accepted `current.recordArrival`. Local continuation supports the same stages; accepted server evidence determines actual arrival. No-answer reports no collection, shipping payment zero and `not-attempted`, without new invented payload fields. Calls/navigation and local pending arrival are not accepted server arrival evidence. Ordered replay can accept a previously captured arrival before accepting no-answer.

## Branch model and predeparture A → B

Migration 0029 adds immutable `b2b_dispatch_cycles.branch_id`, backfills it from each cycle's frozen source snapshot/provisioned branch, and fails closed if ownership cannot be resolved. The migration runs transactionally; its bounded trigger handling preserves closed-cycle history. A fallback insert trigger lets retained ordinary writers inherit the master branch for their initial cycle. Current location/intake reads and historical monitoring/admission/result scopes use cycle ownership. The commercial master identity stays stable; editing its original branch cannot re-scope A history. Authorization filters precede pagination and aggregates. Source/location action-history links also match frozen cycle identity.

1. Preserve accepted A snapshot/action/revisions and its external shipment identity.
2. If prepared, or held before departure without execution history, obtain durably accepted `assignment.withdraw` with current expected source/assignment revisions. A pending/unknown withdrawal does not unlock the goods. A prepared shipment cannot be relocated directly. Unassigned goods need no fictitious withdrawal.
3. Shahn performs and records actual native A handover, carrier transport and B receipt. Tawsel creates no carrier/transport task. Shahn must keep a local custody/dispatch fence across the unknown-result interval; there is no cross-system atomic lock.
4. Send v2 `dispatch.relocateBeforeDeparture` naming `previousDispatchCycleId`, the same external shipment, a fresh `sourceDispatchCycleId`, increasing source revision with exact expected prior revision, the B snapshot and `transfer`.
5. Await accepted original result before B `intake.prepare`/`assignment.receiveBatch`. The new B cycle starts unassigned with assignment revision 0. B independently verifies its receiving driver's enabled B membership and ordinary capacity/planning rules.

Relocation allows only unassigned/withdrawn predeparture cycles with no holder/departure or execution attempt history. It preserves exact line IDs/descriptions/unit due/whole quantities and outstanding shipping/total due. It closes A as non-latest, appends B and an immutable transfer assertion/event, and retains A assignments/source/history. Withdrawn assignment revisions remain on A. An attempt with execution history uses actual return receipt, not relocation. Same source dispatch ID, stale revision, wrong origin, missing B receipt, conflicting identity, changed lines/prices and unauthorized branches cannot silently relocate goods.

## Actual returned A goods → B customer dispatch

1. The A driver's accepted outcome and `return.requestHandover` retain their immutable commercial price, original holder, reported collection, line IDs and A return branch.
2. Authorized ERP `return.confirmSubsetReceipt` confirms only actual A received goods. Requested/offered, held, lost or damaged pieces do not become stock. The command's receiving branch must match the original request's A branch.
3. Shahn transfers eligible actual unallocated received goods from A, records its own B receipt and keeps its native fence. It does not confirm Tawsel return receipt at B for an A attempt.
4. Send v2 `dispatch.createFromReceipt` with the original donor cycle, fresh cycle ID/revision, exact compatible outstanding-price B snapshot and transfer assertion. Whole integer quantities must fit actual received minus prior allocations. Previously collected recipient shipping cannot be charged again; the fresh snapshot explicitly carries correct outstanding shipping and total.
5. On durable acceptance, ordinary B preparation/receipt starts customer execution. A's previous attempt/outcome/money/actual return receipts remain at A. A held discrepancy remains A custody. A future B refusal's return request belongs to B.

The source needs assignment access to current/donor cycle plus intake/assignment access to the transfer origin and provisioned enabled destination. A-only or B-only source cannot transfer A goods to B. Both-branch human staff can inspect both histories, while A-only/B-only staff receive only their cycles. Result/retry authorization uses retained cycle identity; compacted legacy results resolve immutable action/history links rather than guessing from the newest branch.

`transfer` contains original `sourceBranchExternalId`, UUID `transferId`, UUID `destinationReceiptId` and literal `receivedAtDestination:true`. This is a durable source assertion linking Shahn's native receipt, not independent physical proof. False/missing assertion fails validation; repeated destination receipt on the same shipment cannot allocate another cycle. No Tawsel service verifies carrier paperwork or writes Shahn stock. Shahn must enforce true receipt, compatible quantities, exclusive native allocation and durable outbox action identity on its side. Exact public requests/results/history/events/replay/reconciliation from a disposable run are in [interoperability-examples-2026-10-10.json](../verification/interoperability-examples-2026-10-10.json).

Driver/workday/assignment/task locks retain their global ordering, with donor/current assignment locks sorted before task locks; receipt allocation locks and unique constraints provide a single committed winner. Unknown response recovery reuses original action bytes/ID and accepted event identity. A second command cannot reopen the old cycle or allocate the same receipt twice.

## Enrollment and operations

Enrollment mode is `operator-assisted-exact-subjects`. Automatic reservation is incomplete. The installation provides no independently verified trusted issuer-marker writer inventory or approved identity ownership namespace. Admin-only attributes alone do not prove every realm admin is trusted. Neither `erpCompanyId` nor body-asserted `erpCorrelationId` is accepted as reservation authority. Shahn correlation UUID is distinct from principal UUID. No generic capability was enlarged and no remote issuer I/O occurs inside a native transaction.

Shahn collects a nonsecret `EnrollmentRequest` (schema definition): source/company/issuer, exact subject, native principal and distinct correlation UUID, state `pending-operator-reservation`. It has no service endpoint or grant effect. The Tawsel operator independently checks enabled exact subject/issuer ownership and company/source correlation, reviews all trusted writers, and issues a new immutable `integration.bindSource` with the existing identity/credential and increasing source revision adding only exact approved subjects. Bind rejects acquisition of another source's reserved/bound identity. Ordinary user/role/branch/driver provisioning and issuer reconciliation readiness are subsequent independent gates. Duplicate/missing/disabled/conflicting subjects remain pending or rejected; no global token enters ERP. If the exact-subject list exceeds the bounded command limit, stop for reviewed namespace/enrollment design rather than truncating it.

Record explicit bearer expiry in the connection screen. Before expiry, use `integration.rotateCredential` with new ID/hash/expiry and intentional overlap; persist original action/result and deliver the new private scoped material. Never reset source, tenant, actions or inbox to rotate a credential. An expired/revoked bearer requires trusted operator recovery; apply is not an expiry bypass. `integration.disableSource` revokes service access. It does not erase accepted business history.

Install new signing material on protected Tawsel and Shahn configurations before `integration.rotateSigningKey`; retain old verification material until overlap and outstanding/replay deliveries expire. Activation/verify-until IDs are independent from event identity; replay never rewrites retained event bytes. Keep previous key only for its bounded verification window. Remove credentials from retired hosts using the deployment operator's controlled procedure.

For callback migration, approve the exact public HTTPS443 endpoint/DNS/certificate first, retain source/company identity and inbox history, copy processed event/checkpoint state, install the new scoped allowlist/key, and issue revision-checked `integration.configureWebhook`.
