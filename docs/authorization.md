## Identity and membership

`identity_subjects.(issuer, subject)` identifies an authenticated subject and binds it to one stable account UUID. Exact strings are used; do not match by email, phone, username or role name. Subject bindings are retained and disabled, not rebound/deleted. An account belongs to one typed tenant and one membership; company membership requires exactly one tenant-local role. Personal tenants admit one separate account, no company role/branch/integration. Drivers reference a membership, not an unverified token claim. One membership may have multiple branches; there are no per-branch capability grants.

P05 `tenant_keys` and `command_sources` remain durable identity roots. P06 metadata must be explicitly provisioned before these roots confer access; the migration does not guess company versus personal identity for existing keys. Accounts/integrations must reference the matching command-source kind. Business references always include tenant in their foreign key, including branch, role, member, driver and integration. Future feature tables must use the same composite keys; see the disposable resource example in `apps/api/test/support/access-fixture.ts`. A FK protects relationships, not query authorization; the application uses guards, not PostgreSQL row-level security.

Company effective capability is `allow → true`, `deny → false`, `inherit/absent → current role value`; missing role value is false. Role labels are never read by the resolver. Personal access is the fixed own-work set `execution.own`, `correction.own`, `reports.read`, `reports.export`; company exceptions are irrelevant to personal accounts. Explicit integration grants and assigned integration branches are separate from person membership. Services have no driver identity or human impersonation permission, including when their source appears on a driver's trip. P08 must add a verified actor/delegation model before accepting any asserted actor; P06 rejects such service assertions.

## Permission contract table

Every applicable row requires an active tenant, authenticated binding, membership/source, resource tenancy and allowed active branch. Own-driver and source-integration restrictions are additional predicates. A company row without a branch cannot silently become tenant-wide; tenant-level administration must deliberately use `requireCapability` on the already resolved tenant. Personal rows require no branch or integration and their own active driver.

| Canonical capability | Required resource/authority restriction | Lifecycle remains mandatory |
| --- | --- | --- |
| `monitor.read` | Assigned active branches; integration sees its own source records | Read projection only; filter contacts, totals, current/next, history and links |
| `planning.manage` | Assigned branches; `execution.own` may be an explicit alternative for the owning driver | Planning eligibility/current protection, staff predeparture only |
| `location.review` | Assigned branches; explicit `execution.own` alternative for own-driver pin work | Staff review before departure; driver's permitted execution-pin correction only |
| `execution.own` | **Always** the bound active driver, even if a policy requests broad ownership; branch/source checks still apply | Exact operation eligibility, departure/device/assignment/current/revision rules |
| `correction.own` | **Always** the bound active driver | Open-day and dependent receipt/redispatch correction bounds |
| `reports.read` | Assigned branches or personal own work; feature may require own-driver policy | Scoped snapshot/filter definitions; no hidden aggregate totals |
| `reports.export` | Same predicates as the corresponding report; recheck at job run and download | Export snapshot/lifecycle and visibility at delivery |
| `intake.prepare` | Permitted source/branch; verified actor or explicitly delegated service in P08 | Predeparture source snapshot only |
| `assignment.manage` | Permitted source/branch/driver relationship | No staff edits after departure; no direct driver transfer |
| `return.receive` | Actual source branch and authorized source/actor | Driver-requested actual subset, quantity and revision checks; not a general override |
| `return.dispose` | Actual source branch and authorized source/actor | Explicit loss/damage fact; never implies receipt or stock |
| `identity.provision` | Explicit tenant-scoped ERP administration/delegation | Independent identity lifecycle; does not change delivery state |
| `integration.manage` | Explicit bound tenant/source administration | Source/credential lifecycle, no arbitrary human actor |
| `diagnostics.read` | Future P38 adapter must establish its explicit operator and tenant policy | Does not create platform-wide authority in P06 |

`authenticated`, `public`, `local`, `internal`, `external-consumer` and `recipient-scope` in the operation catalog are boundary labels, not role grants. Every later feature must select a server-owned operation policy; request fields must never select capability keys, policy alternatives or the principal. Stable capability vocabulary is checked against the database seed by `authorization-schema.test.ts`.

## Guard inputs and transaction integration

1. Authenticate first: P07 now supplies [real browser sessions](identity.md); P08 still owns service/actor credentials. Pass only a server-created `AuthenticatedPrincipal`: exact issuer+subject for accounts, or the verified stable integration UUID for services. Credentials/session validation, issuer configuration, audience and expiry live in P07, not P06; device generation remains its assigned phase. Never create a production `x-user`, `x-tenant`, `x-role` or test-principal header.
2. Use `withAccess(pool, principal, callback)` for queries/exports or `executeAuthorizedCommand` for resource commands. It locates the tenant, locks the tenant metadata row `FOR SHARE`, then re-reads enabled membership and current grants. The access session expires after the callback; display `AccessContext` is a detached snapshot and cannot authorize subsequent work.
3. `assertScope` checks supplied identity/scope **assertions** against the trusted binding. Omit selectors to use trusted scope, never to widen it. Staff filters such as a chosen driver are ordinary query filters intersected with the authorization predicate, not an assertion that the staff principal is that driver. Exact feature schema validation must reject unknown scope fields, and feature payload IDs must be resolved through the database.
4. A `ResourcePolicy` is a nonempty set of server-owned capability/ownership alternatives. `execution.own`/`correction.own` intrinsically require the bound driver. Call `sqlPredicate(policy, alias, firstParameterIndex)` on a relation exposing `tenant_id`, `branch_id`, `driver_id`, `integration_id`. Values are parameterized; the alias is a server-defined SQL identifier. Apply this predicate **before** joins exposing details, aggregates, pagination, counts and export output. Build source projections from visible rows and redact hidden current/next identifiers/details; full-trip totals are forbidden in a source projection.
5. `requireResource(policy, row)` treats missing and hidden rows alike. `requireOperation(policy, row, eligibility)` first verifies visibility, then evaluates lifecycle. Only load scope from authoritative database rows; body/query ownership is not a resource row. The SQL and row predicates implement the same conjunction; tests exercise both.
6. Commands use `executeAuthorizedCommand(pool, principal, envelope, operation)`. The server adapter fixes `operationId`, validates the exact payload, and supplies `loadAndLockResource`, `eligible`, and P05 domain/progress hooks. Lock order is **tenant access → command identity → driver/workday/assignment/task invariant keys → feature rows**. `loadAndLockResource` locks and reads through the supplied transaction; hooks must never use another pool/connection or perform network work. Recheck revisions, device ownership and all actual feature lifecycle rules while locks are held. Capabilities cannot waive these rules.
7. Replays reauthorize current resource visibility before releasing a stored result, then return the existing result without repeating the lifecycle transition. New lifecycle denial stores a rejected command receipt/evidence and no domain change; scope/capability denial rolls back acquisition and discloses no resource details. The low-level P05 `executeCommand`/`getCommandResult` remain infrastructure primitives, not authorized HTTP adapters. A future result endpoint must associate the action with its authoritative resource policy and recheck visibility before exposing stored summaries/contacts.
8. A job keeps only server-persisted authenticated identity/reference plus business input. Rehydrate authorization at execution, again before publishing/export download, and after external Engine work. Do not serialize `AccessSession`, trust a queue body's tenant/grants, or hold a database transaction during network/file work. Actual workers/export handlers remain their assigned phases; P06 verifies their reusable database guard pattern.

Changes to access tables automatically update the tenant revision under an exclusive row lock. Concurrent guarded work either completes before revocation commits or sees the changed access afterward; both orderings are tested with `pg_blocking_pids`, independent connections and real commits. All callers read current grants, so no invalidation cache is required. This is a deliberate coarse per-tenant administration lock, not a measured high-volume design. Administrative writers should lock the tenant first (P08), write only access rows in that transaction, and retry deadlocks using the same command identity. Do not truncate access tables, disable triggers, mutate them during a guarded read, or run application code as a schema-changing database owner in deployment. Deployment roles and operational load proof remain P39/P38.

Denials expose only `forbidden_resource` with 403 for unavailable access or forged scope, and 404 / `Resource unavailable` for hidden/missing resources. Neither contains hidden IDs, names, counts, tenant, branch, driver or source details. `lifecycle_forbidden` / 409 describes only already-visible resources. P07/P08 must map these to the canonical Problem without echoing database errors or stack traces. Phase-specific lifecycle codes such as `departed_edit_forbidden` may be more precise when the adapter implements that actual rule.

## Reproduce and hand off

Use supported Node 24/npm 11 and the dedicated PostgreSQL setup in [operations](operations.md): `npm run db:local:start`, `npm run db:migrate`, `npm run test:authorization`, `npm run test:database`, `npm run access:demo`, `npm run check`. The demo creates and removes only its marked disposable database. It verifies scoped reads, accepted change/replay, hidden-source denial, lifecycle rejection and disablement.

P07 may rely on `db/migrations/0002_tenant_access.sql`, `apps/api/src/access/{service,command}.ts`, the retained P05 primitives, canonical `CapabilityEffect`, `CapabilityOverride`, `AccessContext` and the real test harness. It must establish actual issuer/session authentication and map subjects to these accounts; no login/password/OIDC claim is proved here. P08 owns provisioning/actor delegation and the ERP-owned editor. No business HTTP operation was promoted from designed.
