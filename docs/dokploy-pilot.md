# Tawsel online team pilot on Dokploy

This procedure is for the `switch2tech.cloud` team pilot. The four Compose projects are separate: Engine, database, application/identity, and mock ERP. The retained root `docker-compose.yml` is a local preprocessing stack and must not be selected in Dokploy. The application and identity/mock databases begin empty; only processed Engine/map assets and the imported Nominatim database are transferred. `.local/snapshots/20260930T145930Z` is an inventory, not a backup.

## Fixed public names and exposure

| DNS name | Dokploy service | Internal port |
| --- | --- | ---: |
| `app.switch2tech.cloud` | `web` | 8080 |
| `auth.switch2tech.cloud` | `issuer-gateway` | 8080 |
| `mock.switch2tech.cloud` | `mock` | 3010 |

Keep `admin.switch2tech.cloud` for Dokploy. Use HTTPS through Dokploy Domains and inspect **Preview Compose** after adding each domain. No domain or host `ports` belong on database, OSRM, VROOM, Nominatim, API, workers, or raw Keycloak. The issuer gateway allows only `/realms/` except master, `/resources/`, and `/.well-known/`; the provisioning worker uses `TAWSEL_ISSUER_ADMIN_ORIGIN=http://issuer:8080` on the application network. Public `/admin` and `/realms/master` must return 404. [Keycloak proxy guidance](https://www.keycloak.org/server/reverseproxy).

## 1. Capacity and target inventory gate

On the actual VPS, record `uname -m`, `free -h`, `nproc`, `df -h`, Docker/Compose versions, Dokploy version, current services/networks and available storage. The local Engine sample was about 6.25 GiB of resident container memory before application, database, Keycloak or Dokploy; it is not a peak measurement. Stop if target RAM/disk cannot support all running services plus data transfer, WAL/archive lag and an isolated restore. Verify target architecture is `linux/amd64` before using the image workflow. Obtain DNS control, a private S3-compatible destination, external SMTP and a protected place for secret/key escrow. Do not paste values into a chat.

## 2. Images, networks and storage

Push the final reviewed source commit. Run **Build pilot images** from GitHub Actions for that exact commit with `app_origin=https://app.switch2tech.cloud`; download its `pilot-image-digests` artifact and copy the seven immutable references into the Compose environment forms. The workflow builds on GitHub Actions, not on the VPS. The Nominatim variant preserves the local imported PG16 format and disables upstream shell tracing that would print its password. Use a GHCR pull credential in Dokploy if the packages are private. Verify all referenced digests can be pulled on the target; never substitute `latest`.

Create distinct external networks named by the environment forms: private Engine, private data, and the inspected Dokploy ingress network. Create named volumes for OSRM processed data, Nominatim PG16 data, Nominatim PBF, PostgreSQL 18 data, PMTiles/maps, and retained web assets. Populate OSRM and maps directly from the local data store or protected object storage, and verify every file against `03-ASSETS-SHA256.json` in the handoff. The source `data/` directory contains one Egypt PBF and three OSRM profile groups; `.local/maps/` contains the Cairo PMTiles/style/fonts/sprites. It is not in Git.

After copying to target volume mounts, run `node scripts/pilot-asset-verify.mjs 03-ASSETS-SHA256.json /path/to/engine-data /path/to/maps` against the mounted volume contents. The command streams each file and fails on missing files, size mismatch or SHA-256 mismatch; a successful copy command alone is insufficient. Supply paths from the target host, never from the workstation in a target check.

Run `node scripts/pilot-nominatim-export.mjs /absolute/private/output-directory` on the local workstation. It verifies the expected volume mount, stops `nominatim-egypt`, exports `nominatim-data` to a tar archive, restarts the container even if export fails, and writes an SHA-256 report. Allow room for the full archive and transfer it through protected storage, outside the chat. Restore into the target **empty** Nominatim named volume and compare the archive hash there before extraction. Preserve file ownership; verify its `import-finished` marker and the image digest before starting the service. The Engine Compose includes a marker guard; it refuses to start Nominatim with an unimported volume. The restored Nominatim database credentials must match the protected file at `NOMINATIM_PASSWORD_FILE` or be rotated safely through PostgreSQL administration before startup. Keep an independently recoverable copy of OSRM/maps/Nominatim outside the VPS. Dokploy Volume Backups cover named volumes, not bind mounts. [Dokploy volume backups](https://docs.dokploy.com/docs/core/volume-backups).

## 3. Database and protected configuration

Use `deploy/database.compose.yaml` with the pinned PostgreSQL/pgBackRest image and an empty named volume. Its first initialization creates restricted owners and separate marked `tawsel_app_pilot`, `tawsel_identity`, and `mock_erp_pilot` databases. The Engine's Nominatim PG16 database is independent. Issue a private CA and PostgreSQL certificate with SAN `database`; store the server key, `pgbackrest.conf`, administrator password and three role passwords only in protected persistent files. Set their **paths**, not their contents, in Dokploy's environment. The image copies TLS and backup files to PostgreSQL-owned files at startup, and reads passwords from file-backed Compose secrets on first initialization. Confirm `sslmode=verify-full` succeeds from the app network and `sslmode=disable` fails. Keep the CA mounted in application, issuer and mock containers. Do not use the local app/identity/mock database files.

Configure the pgBackRest S3 stanza with client-side encryption and escrow its key outside the VPS. After PostgreSQL starts, run `stanza-create`, `check`, and a full backup using the container's `pgbackrest` binary as the `postgres` user, passing `PGBACKREST_CONFIG=/var/lib/postgresql/pgbackrest.conf` to `docker exec`. Install `scripts/pilot-pgbackrest-backup.sh` as `/usr/local/sbin/tawsel-pgbackrest-backup` and the two `deploy/tawsel-pgbackrest-backup.*` units under `/etc/systemd/system/`; put the exact `DATABASE_PROJECT` in a root-owned `/etc/tawsel/database-backup.env`, then enable the timer. The script fails closed unless it finds exactly one running database container for that project. Run the service once manually and inspect the off-host repository; verify the timer is active. This schedules a daily full backup alongside continuous WAL archiving, with retention of seven full backups and their needed WAL chain. Monitor `pg_stat_archiver` and backup age. Restore to an isolated empty volume, verify the three databases and a business checkpoint, and record measured RPO/RTO. The pilot targets are RPO at most 15 minutes and RTO at most 4 hours; a scheduled job alone does not establish either. Also preserve issuer realm/config and app/mock secrets in separate encrypted off-host escrow. [pgBackRest guide](https://pgbackrest.org/user-guide.html), [local recovery limitations](recovery.md).

Dokploy UI values are used for Compose interpolation; they do not automatically enter containers. The application and mock Compose files refer to protected file-backed secrets, and the database file paths must resolve to persistent Dokploy-managed storage **outside a refreshed Git checkout**. Check the effective path and secret mounts in Preview Compose and after a redeploy. Do not share populated files or `docker compose config` output in chat. [Dokploy Compose behavior](https://docs.dokploy.com/docs/core/docker-compose).

## 4. First installation order

1. Check the fresh-install evidence (`kind: initial`) using `npm run deployment:check -- /private/initial-evidence.json`. This mode requires current inventory, empty databases, verified Engine assets and still-closed public domains; it does not invent previous-image, old-queue or backup evidence.
2. Run the Engine Compose and probe all three OSRM profiles, VROOM and Nominatim on their **private** network. Confirm the import marker and PMTiles range response separately from simple container health.
3. Start PostgreSQL and prove TLS/role isolation. Fill a private identity input from the example with all four distinct client secrets, exact app/mock origins and working SMTP; run `scripts/deployment-identity.ts` to create protected realm imports. Mount both imports in the application Compose. Start issuer and its gateway; keep public routes closed at first, then restrict them to the team test IPs while running browser checks.
4. Run application `migrate` and `assets` one-shot jobs, then start API, planning, outbox, provisioning, issuer gateway and web. Verify actual database/schema readiness and private Engine requests. The app domain routes to web only; the auth domain routes to issuer-gateway only.
5. Create team Keycloak accounts through the private administration route using `scripts/deployment-team-seed.ts` and a protected input file. Its private output has immutable subject IDs; feed them into the protected provisioning fixture and mock `adminSubjects`. Bootstrap the source with the temporary operator token, provision roles/branches/users, verify issuer readiness, then remove the bootstrap token if no recovery operation needs it.
6. Run `mock-migrate` on the separate public-test Compose, then start mock, source and projection workers. Use the company realm's `tawsel-mock-erp` confidential client. The mock callback URL must be its exact public HTTPS origin; do not weaken Tawsel's public-IP/SSRF destination rules. Verify DNS and public egress from the outbox container.
7. Complete off-host backup and isolated restore, SMTP, resource headroom, blocked admin paths and an online order lifecycle from mock creation through dispatch, driver outcome, signed callback and applied projection. Fill `kind: go-live` evidence only from observed results, then lift the temporary team IP restriction for the public URLs; application and mock data access still requires authentication. Later upgrades retain `kind: upgrade` evidence and old-queue checks.

The new ChatGPT handoff package is generated with `node scripts/pilot-handoff.mjs [release-images.json]` **after** the final branch is pushed. It contains a pinned source URL, sanitized local inventory and asset SHA-256 list, Arabic stepwise prompt and a file hash manifest. If the image report is omitted, its manifest explicitly says the workflow remains pending.
