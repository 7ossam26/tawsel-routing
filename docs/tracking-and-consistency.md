## Eligibility, departure and current protection

Eligible customer work is received, assigned to this driver, has a confirmed usable execution pin, contains an untouched deliverable portion, and satisfies earliest availability. Prepared work, deferred future work, rejected partial remainders and resolved/lost/disposed goods stay visible in their correct groups but are not executable customer stops. Urgency does not bypass eligibility.

The admission limit is 50 **remaining planned stops**, including planned branch visits. Co-located shipments each count. It is neither a daily cap nor a cap on all held records. Reject a new over-limit batch atomically; do not silently split it or create a phantom backlog. Retry/reactivation must pass current admission. Failure to admit does not delete the existing held record or prevent recording a physical outcome.

Online start atomically publishes the chosen ready/manual plan, locks dispatched snapshots, creates/reuses the open workday, establishes the one active round and device generation, and captures the first forecast. Lock start against predeparture withdrawal/reassignment. New received work admitted to active execution acquires the same departure protection. ERP staff cannot then change recipient/content/price/assignment/outcome/urgency. Driver pin correction, assigned-driver urgency and bounded self-correction remain allowed. Native source-branch receipt/disposition is a narrow exception, not a staff override. Identity administration remains separate.

Current is either absent, heading, arrived or branch service. Selecting heading is explicit; navigation/call/WhatsApp links are local UI actions with no execution transition. Arrival is explicit. Automatic replanning preserves current; eligible urgent work follows it, then ordinary work, respecting earliest times. After resolution current clears; showing next planned does not claim heading. A phone outcome without arrival leaves last confirmed physical origin unchanged. First origin is confirmed branch/manual; later origin is last explicit physical stop. No GPS is collected.

Branch interruption may pause heading-to-customer work; arrived/handled customer work must first resolve. P22 must verify the master-plan proposal at full capacity: publish a visible branch-service segment, retain the paused customer sequence, count branch stops against that active segment, then resume/replan it. This is not automatic splitting of an incoming addition batch. No second round or disappearing shipment is permitted. Claimed returned subsets wait for server-confirmed receipt before resume; unresolved other items remain held/disputed without a whole-batch gate. The detailed full-capacity concurrency proof remains P22 work, not an extra permission decision here.

## Atomic acceptance and recovery

Every accepted command must authenticate and scope, acquire consistent invariant locks, check lifecycle/revisions/ownership, write domain state plus effective progress, immutable history/audit, durable idempotency result and required outbound intent in **one** PostgreSQL transaction. All commit or all roll back. P05 implements the transaction and lock protocol below; feature phases add their rows under that order. Provider/issuer/ERP HTTP is outside that transaction. Persist planning intent before asynchronous Engine work; provider outage does not reverse accepted receipt/outcome.

Idempotency key is `(tenantId, authenticated command source, actionId)`. The authenticated source is stable across token refresh and cannot be chosen by an untrusted body. Same key plus same semantic payload returns the established result; different payload raises `IdempotencyConflict` with status 409/code `idempotency_conflict`, for a future authenticated HTTP adapter to map to the canonical Problem. Query/retry an uncertain response with the same action ID. Do not generate a new ID to escape uncertainty or an expired response body; retained identity/result tombstones prevent re-execution.

### Implemented P05 transaction protocol

The dedicated application schema is `tawsel`, migrated only through `apps/api/src/db/migrate.ts` and `db/migrations/*.sql`. PostgreSQL 18 connections require a checked database name, owner and explicit purpose comment. P05 owns tenant/source keys, command identities, audit, rejection evidence and outbound intent. P06 adds typed tenants/accounts/subjects/memberships/roles/branches/drivers/integrations and [transactional authorization](authorization.md); no shipment table is implied. Composite foreign keys include tenant and source/action identity. Outbox recipients must exist as integration keys in the same tenant; later event producers/senders must also apply current recipient visibility.

The internal `executeCommand(pool, trustedScope, envelope, hooks)` boundary expects the caller to authenticate, authorize and validate its exact feature payload first. P06 supplies `executeAuthorizedCommand` and `withAccess`; P07/P08 must authenticate real subjects/services. P06 holds the tenant access lock before command acquisition and uses the same transaction; visibility is rechecked even on replay, while new commands also check locked lifecycle. An account source is a stable account UUID; an integration source is a stable integration UUID, not a token/session/device ID. Body tenant/source/asserted actor must agree with the trusted binding. Envelope validation is strict Ajv 2020-12; accepting a generic envelope alone does not authorize or validate a feature. `getCommandResult` requires the same trusted tenant/source but its future adapter must additionally recheck associated resource visibility; there is no unauthenticated HTTP endpoint.

Hash version 1 is SHA-256 over strict canonical JSON of `{envelope, actorId: trustedActorOrNull}`. It includes operation/schema/payload versions, resources, all base versions, dependencies, device/observation fields and payload. Sort object keys by JavaScript UTF-16 order; preserve array order and string bytes; encode finite numbers with JSON.stringify (`-0` equals `0`). Reject undefined, nonfinite numbers, sparse arrays, dates/class objects, symbols and cycles. No Unicode normalization or field omission/defaulting occurs. HTTP headers, credentials, transport retry times and server-generated receipt/commit times are not inputs. Callers must preserve the original envelope. Snapshot and freeze it before asynchronous work and pass that snapshot to feature hooks; hooks must use the supplied snapshot and scope.

One checked-out `pg` connection runs `READ COMMITTED`, `synchronous_commit=on`, lock timeout 3 seconds, statement/idle timeout 10 seconds and transaction timeout 15 seconds. These are bounded engineering defaults, not measured capacity claims. Every query is awaited. PostgreSQL unique key acquisition uses `INSERT ... ON CONFLICT DO NOTHING`, followed by a new `SELECT ... FOR UPDATE`: a concurrent duplicate waits for the first writer, then reads its committed result; a rolled-back first writer allows the waiting command to execute. There is no application mutex or automatic retry under a new identity. A lost COMMIT response is unknown until same-ID recovery.

Lock order for feature code is:

1. P06 resolves authenticated identity and takes the tenant access row lock before command work; retain it to commit. Permission administration must take this tenant lock before changing access rows.
2. Acquire the single command identity; never nest command execution or lock another action while holding feature rows.
3. Call `lockInvariants` **once with the complete guard set**, ordered driver → workday → assignment → task, then lowercase UUID byte order within each kind. The PostgreSQL transaction advisory guard includes tenant and kind and works before a feature row exists. Hash collisions can only add serialization; database constraints remain mandatory.
4. Acquire/read feature rows in that same hierarchy and UUID order, authorize visibility, then check lifecycle/revisions and write domain/progress/history. The authorization loader only locks/reads, never performs tentative mutations before the domain savepoint. Later phases must document extensions and share guards across competing operations (start/assignment, receipt/correction, closure, etc.). Do not acquire a lower-ranked guard afterward.
5. Append audit, insert outbound intents ordered by recipient/event ID, then finalize the durable response/receipt/summary. A deferred constraint rejects commit of an unfinished acquisition.

The handler supplies `writeDomain` and `writeProgress` on the same connection. An accepted result commits these writes with audit and all supplied intents. A rejected/review decision rolls back the domain savepoint (including any tentative feature writes), then commits the original envelope as `command_evidence`, a distinct rejected/review audit entry and its durable response. Rejection never gets a business `committedAt`; a system/SQL exception rolls the entire command back, with no evidence-receipt claim. Fault hooks are test/observability seams, not an authority mechanism.

`receivedAt` is server acquisition time and `committedAt` is the server acceptance timestamp sampled before final result persistence; both become externally visible only after successful COMMIT. It is not PostgreSQL's physical WAL commit timestamp. Outbox `created_at` is intent creation time; its `pending` state proves neither sending nor ERP receipt/application. P25 adds recipient ordering and transport/signed envelope assembly without changing the stable event identity. Network work, transaction-control SQL and detached/unawaited queries are forbidden inside feature hooks. Prepare network inputs before the command or persist intent and work afterward. Connection failure destroys the checked-out connection and rejects the command, including while a hook waits.

### Implemented response retention

`compactCommandResponses(pool, limit)` is an explicit bounded operation (default 100, maximum 1,000), with no scheduled purge. Database time enforces **at least 30 days after finalization**. It locks eligible identity rows in tenant/source/action order with `SKIP LOCKED`; it removes only full response body/status. Receipt, hash/hash version, operation identity, actor, stable feature summary and audit/evidence remain indefinitely in this foundation, satisfying at least business-record lifetime. Future deletion policy must not resurrect identities.

Pending/review work, `retention_hold=true`, and any unresolved associated outbox intent prevent compaction. Rejected feature decisions can explicitly request a hold too. No evidence, audit or outbox payload is purged. No P05 worker marks an intent resolved; later resolution must lock the command identity before changing associated intent/hold state to serialize with compaction. Compacted duplicates return canonical `ActionResult` with `retention=compacted`, original receipt/summary and no response, never invoke the domain hook, and still conflict on a changed hash. Clients must reconcile/query the referenced records when released, not retry as a new command. Feature summaries must contain minimal stable identities/revisions, not full responses or personal contact details.

Validation for an outcome uses the current compatible task snapshot, assignment/attempt, effective outcome and device authority. A newer route revision alone is not grounds for rejection. Changed price/content, dependent handover, day closure or stale ownership is different. No universal last-write-wins or equality check against every known revision.

Correction is by the owning driver during the open workday before dependent branch receipt/redispatch, with quantity/money validation and preserved original history. It races with receipt, redispatch and day end under shared locks. No staff correction endpoint, refund authority or reversal of actual receipt is created. Former-device actions receive durable evidence identity and review/conflict result; current owner may adopt compatible evidence through the same bounded correction rules. Keep rejection and provenance even if adoption is forbidden. Received restricted evidence does not grant a revoked account execution rights.

Client local journal action and pending projection share one IndexedDB transaction (P33); storage failure cannot show saved success. Replay waits for dependencies and same-account authentication. Save returned receipt before retiring pending state. Pending overlays remain separate from confirmed snapshots. Start, takeover, optimization and ERP branch receipt require connectivity; already-started downloaded execution can continue within allowed offline actions. Roughly 24 hours is a support target, never an evidence deletion timer. No forced update/reload with pending work; keep versioned old payload readers (P34–35).

Integration events use at-least-once delivery with durable idempotency, not exactly-once networking. Domain transitions/corrections have immutable event IDs. Replacement progress snapshots can be superseded, but a later snapshot cannot erase a missing quantity/receipt event. One recipient's sequence must not disclose another integration's hidden events. Poll scoped coherent snapshots with conditional revisions; freshness, last action, device contact, receiver receipt and projection application are separate observations. The one-second poll/ten-second stale defaults and event-replay retention remain engineering proposals to verify in P24–26/P38; the P05 command-response floor is implemented above.
